The matching private fixture-server scenario is `worker-active-resume`: first singleton generation succeeds, the second waits **120 seconds**, and subsequent generations succeed immediately. Count-token calls do not advance that sequence. No cloud provider is called.

The test uses a disposable two-page job and synthetic local credential, with quality review explicitly disabled. It preserves global preferences and installed model packs.

At one committed page and two app `Request started` events, the test requires exactly one owned WorkInfo in `RUNNING` and the job in `TRANSLATING`. It records `before_resume_while_worker_running`, calls the same public per-job `manager.resume(jobId)` used by queue UI, and records the appended WorkInfo in `after_resume_while_old_worker_unfinished`. There is **no prior Pause or wait for old Worker teardown**. This is a public-action/actual-WorkManager boundary test, not notification UI acceptance or a simulated coroutine graph.

This barrier does not wait for the second host dispatch. Nearby, non-atomic host/device clock samples suggest that dispatch was about 0.10 s after Resume before the fix and about 0.09 s before Resume after the fix; they do not establish exact causal timestamps. The active-job reproduction is supported, but identical already-server-accepted transport boundaries are not claimed. The kept-awake, externally powered run also does not establish natural idle, screen-off or Force-stop recovery.

Completion must occur within **90 seconds of the Resume call**, including enqueue-observation overhead. A passing result additionally requires both saved pages, the exact original first result/revision, unchanged original file hashes, three generation starts, finished owned WorkInfos and unchanged global settings. Independently reconcile the host ledger: the first page is dispatched once; only the interrupted second page is dispatched twice. Preserve old/new WorkInfo IDs, attempts, stop reasons and background events from the report.
